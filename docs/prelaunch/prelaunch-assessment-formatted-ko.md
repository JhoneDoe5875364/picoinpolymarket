# PredictPix 사전 출시 평가 — 응답 문서

________________________________________
## 문서 목적
prelaunch.md(108–115행)에서 제기된 질문에 대한 답변으로, 현재 PredictPix 코드베이스 및 프로덕션 준비 프레임워크 분석을 기반으로 작성됨.

________________________________________
## 경영 요약
PredictPix는 이미 동작하는 MVP를 보유하고 있음: Pi 인증, 마켓, 거래, 내부 잔액, 청구 플로우, 관리자 패널, 댓글, 지역 제어 기능이 구현되어 있음. 사전 출시 프레임워크는 잘 구성되어 있음. 본 평가는 안전한 출시를 위한 필수 항목과 출시 후 개선 목표를 구분하고, 단계별 구현 순서를 제안하며, 최소 실행 가능 출시 기준을 정의하고, 작업을 복잡도별로 그룹화함.

________________________________________
## 1. 기술적 필수 vs 출시 후 개선

### 기술적 필수 (프로덕션 필수)

| 영역 | 내용 | 이유 |
|------|------|------|
| **인증 및 지갑** | 안전한 Pi SDK 플로우, JWT 액세스 토큰, 클라이언트 노출 API 키 제거, 예측 전 서버 측 잔액 검증, 인증 엔드포인트 속도 제한, 안전한 비밀 저장소 | 없으면 사용자 악용, 잔액 조작, 시스템 악용 가능 |
| **마켓 생명주기** | 관리자 전용 생성, 명확한 상태 전환(최소: open → resolved), 마감 후 예측 방지, 타임스탬프 기반 잠금 | 마켓은 결정적으로 동작해야 함; 마감 후 예측은 지급에 오류 발생 |
| **포지션 및 노출** | 거래 전 서버 측 잔액 확인, 이중 지출 방지, 멱등 트랜잭션 제출, 경쟁 조건 방지 | 현재 코드는 POST /positions 전 잔액 검증 부재; 경쟁 조건으로 인한 초과 인출 가능 |
| **보상 분배** | 결정적 지급 계산(기존 존재), 멱등 지급 처리, 지급 상태 추적, 감사 추적 | 지급 로직은 문서화되어 있고 동작함; 감사 가능성 및 상태 추적 필요 |
| **데이터베이스 강화** | 민감 테이블 RLS 정책, 의도치 않은 공개 쓰기 접근 차단, 외래 키 제약 | Supabase/Postgres 보안 기본; 데이터 유출 및 무단 쓰기 방지 |
| **댓글** | 단일 표준 댓글 테이블(존재), 속도 제한, 기본 스팸 방지 | 공개 콘텐츠는 제어 가능해야 함 |
| **관리자 패널** | 마켓 생성/편집/해결(존재), 사용자 조회(존재), 긴급 전역 거래 중지 | 중지 스위치는 사고 대응에 필수 |
| **보안 및 인프라** | HTTPS 적용, 환경 변수 격리, 디버그 엔드포인트 비노출, 오류 로깅 | 프로덕션 기본 보안 |
| **투명성** | 공개 규칙 페이지, 수수료 공개, 이용 약관, 면책 조항 | 예측 마켓의 법적 및 신뢰 요건 |

### 출시 후 개선 (Aspirational)

| 영역 | 내용 | 비고 |
|------|------|------|
| **인증** | 단기 JWT + 리프레시 로테이션, 지갑 소유권 검증(서명 기반), 계정당 한 지갑 | MVP 차단 아님; 단계적 적용 가능 |
| **마켓 생명주기** | Draft → Active → Locked → Resolved → Finalized 전체 흐름, 해결 감사 로깅, 관리자 오버라이드 로깅 | 거버넌스에 유용; 출시 후 추가 가능 |
| **포지션 및 노출** | 거래당 가격 변동 상한, 사용자/마켓별 노출 한도, 거대 참여자 방지 로직 | 규모 확장에 중요; 단순한 한도로 시작 가능 |
| **보상 분배** | 전송 전 수동 검토 체크포인트, 전용 지급 원장 테이블, 관리자 지갑 잔액 가시성 | 운영 제어 개선; 점진적 추가 가능 |
| **데이터베이스** | 인덱스 최적화, 마이그레이션 추적(예: Alembic), 시점 복구, 백업 설정 | 성능 및 운영 개선; 소규모 출시에 차단 아님 |
| **댓글** | 소프트 삭제, 전체 모더레이션 도구 | 기본 속도 제한 및 스팸 제어로 초기 충분 |
| **관리자** | 마켓별 노출 뷰, 관리자 감사 로그 가시성 | 운영 개선; 차단 아님 |
| **보안** | 방화벽 설정, SSH 키 전용 접근, fail2ban, 로그 모니터링, 알림 | 인프라 강화; 초기 출시 후 적용 가능 |
| **재무 통제** | 플랫폼/운영 지갑 분리, 가스 예비 버퍼, 일일 원장 조정 | 규모 및 규정 준수에 중요; 단계적 적용 가능 |
| **투명성** | 해결 정책 문서화, 보상 시점 공개, 버전 관리 업데이트 로그 | 신뢰 향상; 출시 후 추가 가능 |

- 관리자 노출 뷰 및 감사 로그 가시성
- 해결 감사 로깅 및 전체 마켓 생명주기(Draft → Finalized)
- 재무 통제(지갑 분리, 조정)

## 3. 진정한 최소 실행 가능 출시 기준

### 정의
사용자가 안전하게 거래하고, 승자가 올바르게 지급받으며, 긴급 시 시스템을 중지할 수 있을 때 출시가 가능함.

### 출시 전 필수 조건

| # | 조건 | 상태 | 조치 |
|---|------|------|------|
| 1 | 잔액 부족 시 예측 불가 | **미구현** | POST /positions에 서버 측 잔액 검사 추가 |
| 2 | 이중 지출/경쟁 조건 초과 인출 방지 | **위험** | 멱등성 + 잠금 추가 |
| 3 | 마켓 마감 후 거래 없음 | **검증 필요** | 거래 수락 전 closes_at / end_date 적용 |
| 4 | 지급 계산이 결정적이고 감사 가능 | **존재** | 문서화 및 유지 |
| 5 | 관리자가 모든 거래 중지 가능 | **미구현** | 전역 중지 플래그 추가 및 거래 엔드포인트에서 적용 |
| 6 | 인증 엔드포인트 속도 제한 | **미구현** | 속도 제한 추가(예: slowapi 등) |
| 7 | 클라이언트에 API 키 노출 없음 | **검증 필요** | 프론트엔드 및 env 변수 감사 |
| 8 | 수수료 및 규칙 공개 | **부분적** | 규칙 페이지 및 수수료 공개 추가 |
| 9 | RLS로 무단 데이터 접근 방지 | **미확인** | Supabase RLS 정책 감사 |
| 10 | 프로덕션 HTTPS | **가정** | 배포 설정에서 확인 |

### 요약
최소 실행 가능 출시: Phase 1(위 1–4번) 완료 및 5–10번 검증. Phase 2는 위험 수용 가능 시 소프트 출시와 병행 가능.

## 4. 대략적 복잡도 그룹

### 낮은 노력 (각 1–3일)

- 전역 거래 중지 스위치 — trading_frozen 플래그 추가; 거래 엔드포인트에서 확인
- 수수료 공개 페이지 — 정적 콘텐츠; 푸터에서 링크
- 공개 규칙 페이지 — 정적 콘텐츠
- 인증 속도 제한 — slowapi 또는 유사 미들웨어 사용
- 디버그 엔드포인트 없음 확인 — config/env 감사
- 기본 댓글 속도 제한 — 댓글 엔드포인트에 사용자/IP별 제한

### 중간 노력 (각 3–7일)

- 서버 측 잔액 검증 — POST /positions에 검사 추가; 엣지 케이스 처리
- 멱등 트랜잭션 제출 — idempotency 키; idempotency 테이블
- 마감 후 예측 방지 — 거래 플로우에서 closes_at / end_date 검증
- RLS 정책 — 주요 테이블에 정책 정의; 철저 검증
- 클라이언트 노출 API 키 제거 — 감사 및 백엔드 전용으로 이동
- 기본 스팸 방지(댓글) — 빈도 제한, 단순 휴리스틱

### 높은 노력 (각 1–3주)

- 경쟁 조건 방지 — 행 수준 잠금, 낙관적 동시성 또는 큐
- JWT 리프레시 토큰 로테이션 — 새 토큰 플로우, 리프레시 엔드포인트, 저장소
- 지갑 소유권 검증 — Pi SDK 통합, 서명 검증
- 전체 마켓 생명주기(Draft → Finalized) — 스키마 변경, 새 상태, 마이그레이션
- 지급 원장 + 수동 검토 — 새 테이블, 관리자 UI, 워크플로우
- 사용자/마켓별 노출 한도 — 비즈니스 규칙, 스키마, 검증 로직
- 재무 통제(지갑 분리, 조정) — 아키텍처 및 프로세스 설계

## 5. 광고 — 평가

### 고려사항

- **사용자 경험**: 예측 마켓은 집중이 필요함; 침습적 광고는 참여도를 저하시킬 수 있음. 전면 광고보다 배너, 스폰서 섹션 등 비침습적 배치 선호.
- **수익 vs 신뢰**: 광고는 성장 자금을 지원할 수 있으나 신뢰를 해치지 않아야 함. 예측 콘텐츠와 충돌하는 광고(예: 도박, 빠른 부자 되기) 피함.
- **기술 통합**: Google AdSense, 맞춤 스폰서, Pi Network 생태계 파트너 등 옵션. 광고 안전 로드(CSP, 악성 스크립트 없음) 확인.
- **규제**: 일부 관할권은 예측 마켓을 도박으로 간주; 광고 정책이 특정 배치를 제한할 수 있음. Pi Network 및 플랫폼 광고 정책 확인.

### 권장사항

- **단기**: 광고를 출시 후 개선 목표로 취급. 출시와 핵심 수익(예: 수수료)에 집중.
- **출시 후**: 광고를 점진적으로 도입:
  - 단일, 제어된 배치(예: 푸터 또는 사이드바)로 시작
  - 화이트리스트된 관련 광고주 사용
  - 참여도 및 신뢰에 미치는 영향 모니터링
- **대안**: 일반 광고 네트워크 전에 Pi Network 생태계 파트너십 또는 스폰서십을 첫 수익원으로 검토.

## 부록: 현재 구현 스냅샷

| 사전 출시 영역 | 구현됨 | 부족 사항 |

| 10. 투명성 | 이용 약관, 개인정보, 소개 | 규칙 페이지 없음, 해결 정책 없음, 수수료 공개 없음 |
